Wheelhouse for Mac

Security model

Wheelhouse is built so that a slip, a wrong terminal, a script or an AI agent cannot change a production cluster by accident. This page says how, and just as plainly where the protection stops.

In short: every change Wheelhouse makes or hands out credentials for goes through one rule set. Production changes need a typed confirmation. Read-only clusters refuse changes. Tools that bring their own credentials, and shells that use your own ~/.kube/config, are outside what Wheelhouse can guard.

One gate for every change

The app’s own actions, the Manifest Editor, Chart Room, Tides, Survey fixes, First Mate proposals, Beacon requests and the tools you run in a Deck Terminal all pass through the same policy and the same confirmation sheet. There is no second path to a cluster’s write operations inside the app.

Environments

  • Production (shown in rose, with a shield, used for nothing else): every change needs a typed confirmation, naming the object, the release, the app, the count or the cluster. This cannot be turned off.
  • Read-only: changes are refused and change buttons are hidden. Interactive shells and port-forwards are refused unless you allow them for that cluster.
  • Discovered clusters (from your kubeconfig files or from Landfall) start read-only. Names that look like production are suggested as Production; nothing is applied without you seeing it.
  • Lowering safety (allowing changes on a production cluster, changing Production to something else, turning Beacon on, allowing Beacon change requests, or turning on Direct mode for a terminal) asks for Touch ID or your login password and is written to Activity. Raising safety never asks. Using a bypass inside a terminal (see below) is not blocked and does not ask; the pane just shows Unguarded.

Gangway: the guard for terminals and command-line tools

Gangway is a small proxy inside the app that listens on 127.0.0.1 only. Each guarded session (a Deck Terminal, a Helm run from Chart Room, a Flux diff) gets a temporary read-only kubeconfig that points at Gangway with a one-off token. Gangway forwards allowed requests to the real cluster with the real credentials, so cloud sign-in works but the shell never sees the credentials.

On Production, a single plain kubectl, helm or flux command can be approved once. The approval covers only that command, on that cluster, from that terminal, until the prompt returns (ten minutes at most). Anything else, such as scripts, pipelines, watch, full-screen tools and AI agents running in the terminal, is confirmed request by request. A declined or unanswered sheet (120 seconds) becomes a 403 that kubectl prints.

Gangway closes open exec and port-forward streams when the app locks, when a cluster becomes read-only or Production, and when the session ends.

Confirmation sheets that come from something else

A sheet requested by First Mate, Beacon or a terminal has no default button (Return does nothing, Escape cancels), ignores input for about one second after it appears, and each source can have only one request waiting. On Production these sheets require typing (the one exception is the plain button confirmation for an interactive pod shell, exec or port-forward), and the typed field accepts only real keyboard input (not pasted, synthetic or accessibility-injected text).

Things that are inserted, never run

Commands from First Mate and Copy kubectl Command are placed at the terminal prompt. Hidden and direction-changing characters are removed first (the terminal tells you how many), the text goes in without a newline, and it is refused if the terminal is on a different cluster than the command. You press Return, and Gangway still guards it. The only text Compass ever runs is the text you typed after !.

Secrets

Secret values are masked. Revealing or copying one needs Touch ID or your password, and a copied value is cleared from the clipboard after 60 seconds. Secret values are kept out of widgets, notifications, the Compass index, First Mate and Beacon (they see key names only), Survey exports and logs. Helm values are masked by key name.

AI and agents

  • First Mate has read tools and proposal tools only. A proposal opens the normal review, marked “Proposed by First Mate”. It cannot type a confirmation or press a button.
  • Beacon is off by default and read-only by default. Change requests are optional per client and per cluster, are never available for Production or read-only clusters, and always need your confirmation in the app. Results sent to an agent are labelled as untrusted cluster data.

Audit

The Activity window records the time, cluster, action, object and result of every change, and where it came from: the app, Chart Room, Tides, Survey, First Mate, a Beacon client or a terminal command. It also records every stream, proxy request and impersonation attempt Gangway saw. Activity stays on your Mac, can be exported, and never contains Secret values or request bodies.

What is not guarded

Please read this part.

  • Other terminals. Terminal.app, iTerm, an editor’s terminal or a CI job that uses your own ~/.kube/config are outside Wheelhouse. It cannot stop them.
  • Tools with their own credentials such as aws, argocd and terraform are not guarded, even when run inside a Deck Terminal.
  • Bypass inside a Deck Terminal. If you point KUBECONFIG elsewhere, or use --kubeconfig, --server or --token, the pane shows Unguarded (with a Restore button). Wheelhouse tells you; it cannot prevent a determined user in their own shell.
  • Direct mode is an optional, per-cluster setting that gives a terminal a kubeconfig for that one cluster with no guard. It is off by default, needs Touch ID or your password, and is never available for Production or read-only clusters.
  • Agents with their own shell can bypass Beacon entirely, because Beacon only guards what goes through Beacon.
  • The command line shown on a sheet is reported by your shell and is a hint. The request itself is what is confirmed.
  • Wheelhouse does not protect against malware running as you on your Mac, or against someone who has your unlocked Mac. Use the app lock (Touch ID or password, also on wake and when the screen locks) for the second case.

Reporting a problem

If you find a way around a guard described here, please tell us privately first; see Support.
