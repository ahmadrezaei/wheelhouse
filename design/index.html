Wheelhouse

Every cluster, at the helm.

A native iPhone and iPad app for operating a fleet of Kubernetes clusters: a fleet-wide health report, per-cluster dashboards, full resource management, logs, shells, YAML with server-side dry-run, and port-forwarding — with production-grade safety rails. This board shows the proposed design for approval; the written spec is in DESIGN.md.

01Identity & design system

App icon in the three iOS appearances, semantic color tokens, Dynamic Type scale, spacing and the small set of components reused on every screen.

Icon concept. A ship’s helm seen from above: a glass rim and hexagonal hub, with six spokes ending in hexagonal handles — each handle is a cluster node, the wheel is the operator steering the fleet. A faint compass bearing ring sits behind it. Deliberately not the Kubernetes mark: no heptagon, no seven spokes, no blue badge shape; circular rim and hex handles are Wheelhouse’s own geometry. Foreground is layered (rim, spokes, handles, hub) so it can be split into Icon Composer layers for Liquid Glass specular highlights.

02Information architecture

iPhone uses a four-tab floating glass tab bar plus a search tab; iPad uses a three-column split view. Both share one router and the same screens.

iPhone · TabView (compact)
  • Fleet — fleet dashboard → cluster → resource; toolbar: Settings, Alerts inbox, Add Cluster
  • Cluster — dashboard of the current cluster; title menu switches cluster
  • Resources — Workloads · Networking · Config · Storage · Cluster · Access · Custom Resources → list → detail
  • Sessions — port-forwards, shells, followed log streams
  • Search (search-role tab) — across kinds in the current cluster, scope “All clusters”
iPad · NavigationSplitView (regular)
  • Sidebar — Fleet, Alerts, Sessions; Clusters (disclosure → resource sections); Settings
  • Content — fleet cluster list, or resource list for the selected section (namespace, label filter, sort, search)
  • Detail — cluster dashboard or resource detail; logs/shell/YAML can split the detail pane or open in a new window (multi-window scenes)
  • Compact width (Slide Over, narrow Split View) falls back to the iPhone TabView
Why this model
  • Tabs map to the 4 jobs: scan the fleet, inspect one cluster, manage resources, keep sessions open
  • A sidebar-adaptable TabView can’t express clusters × sections hierarchy, so iPad uses an explicit 3-column split view sharing the same view models and routes
  • Current cluster + namespace are app-wide state, always visible as a context line on resource screens (safety)
  • Deep links wheelhouse://cluster/<id>/ns/<ns>/<kind>/<name> used by widgets and notifications

03Dashboards — iPhone, light & dark

The “full report”: fleet overview across every cluster, then a dense but calm per-cluster dashboard. Content scrolls inside each device.

04Workloads & detail

Lists optimised for scanning, details optimised for action. The production confirmation is the single pattern used for every destructive action.

05Logs, shell, YAML

Power tools that still feel native: monospaced, high-contrast, keyboard-friendly.

06Nodes & sessions

Cluster operations with explicit previews of impact, and one home for everything long-running.

07Onboarding, import & settings

Add a cluster in under a minute; understand exactly why a context can’t be imported; control safety, sync and alerts per cluster.

08Security & error states

Locked, masked, unreachable and forbidden — each with a clear cause and next step.

09iPad

Real multi-column layout, pointer and hardware-keyboard first. Columns scroll independently.

10Widgets, Lock Screen & notifications

Small, medium and large Home Screen widgets (light and dark), Lock Screen accessories and time-sensitive alerts. Widgets read a snapshot from the App Group; they never contain credentials or secret values.

11Key flows

The six journeys the design is optimised for. Every mutating step ends in the same confirmation pattern.

Onboarding & add cluster

Welcome → Try Demo or Add Cluster → Kubeconfig / Token → Connection test (version, RBAC, metrics) → Environment + read-only + iCloud → Fleet dashboard

Kubeconfig import

Files · Paste · Share Sheet → Parse (Yams) → Validate each context → Exec / auth-provider → disabled + explanation → Pick contexts → Keychain → Add N clusters

Triage a CrashLoop pod

Notification / Needs Attention → Pod detail (diagnosis banner) → Logs → Previous → Find “OutOfMemory” → Edit Deployment YAML (limit) → Diff + dry-run → Apply or Restart

Edit YAML → diff → apply

YAML action → Editor (lint) → Review: server dry-run → Diff vs live → Conflicts? Force needs confirm → Prod: type name → Server-side apply

Drain a node

Nodes list → Node detail → Drain sheet: pods, options → PDB pre-check → Type node name (prod) → Cordon → evict with progress → Done · Uncordon later

Port-forward

Service / Pod → Forward → Pick port → local port → WebSocket portforward → Sessions list → Open in in-app browser → Stop / auto-reconnect on return
